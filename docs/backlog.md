#### 학교 직접 호출 위험 정정 (2026-04-26)

처음엔 🔴 로 평가했으나 실제 사용자 동선과 미러 정책 상 위험 거의 0:

- 8일 이상 과거 메뉴 굳이 찾는 사용자 자체가 거의 없음
- 사용자가 76개 학교에 분산 → 한 학교 동시 폭주 자체가 드묾

남은 유일한 빈 창은 **새 학교 등록 직후~다음 cron 까지 (최대 8시간)** —
이건 **규칙으로 해결**: 학교 추가 후 Vercel Dashboard 에서 cron 수동 실행
(`AGENTS.md` 의 "학교 추가는 한 곳만" 섹션에 명문화).

→ "학교 폴백 제거" 사전 처방 우선순위가 매우 낮아짐. 다른 사전 처방 (캐시
헤더, Analytics) 가 더 임팩트.

### 폭증 발생 시 즉시 대응 카드

진단 시점에 빠르게 결정:

1. **Vercel Pro 업그레이드** ($20/월) — 즉시 적용. 함수 한도 100K → 1M.
   비영리 톤이라 망설여지나 한도 초과로 전체 다운보다 나음
2. **Cloudflare 앞단** — 무료. 도메인 nameserver 변경 → CDN 추가 캐싱
3. **유지보수 페이지 토글** — 환경변수 `MAINTENANCE=1` 인 simple HTML 미리
   만들어 두기. 한도 초과 시 다운 대신 의도된 점검 페이지 노출
4. **자체 서버 이전** — Hetzner/Oracle Free Tier. 시간 걸림 + 운영 부담 큼

### 사전 처방 (실행 시 작업 순서)

폭증 전에 미리 깔아두면 한도 더 늦게 도달:

1. **`/api/meal/photo` 학교 폴백 제거** — 미러 only 로 변경. 미러에 없으면
   "사진 준비중" 으로 표시. cron 이 어차피 하루 3회 워밍하니 시간 지나면
   자동 미러링됨. **cascade failure 영구 방지가 핵심**
2. **`/api/meal` 응답 Cache-Control 추가** — `public, s-maxage=1800,
   stale-while-revalidate=86400`. CDN 30분 캐시 → 같은 (학교·날짜) 함수
   호출 1회로 압축
3. **미러 miss 캐시 시간 늘리기** — `src/app/api/meal/photo/route.ts` 의
   `CACHE_SHORT` (현재 60초) → 1800 (30분). 어차피 cron 30분 내 안 도니까
4. **`@vercel/analytics` 설치 + layout.tsx 끼움** — 무료. Web Vitals + 함수
   호출 추적 시작
5. **Vercel Dashboard 작업** (사용자 직접):
   - Analytics 탭 → Enable
   - Settings → Usage → Alert 임계값 (예: 70%) 설정

### 트리거 조건 (언제 위 처방 실행하나)

다음 중 하나라도 true 면 사전 처방 실행:
- 카톡 단톡방 홍보 결정 직전
- 사이트 일일 진입 100명 이상 안정화
- Vercel Analytics 에서 함수 호출 한도 50% 도달

### 의도적으로 안 하는 것 (당분간)

- **rate limit 미들웨어** (next-rate-limit 등) — Vercel CDN 캐시 강화로
  대부분 흡수. 진짜 abuse 보면 그때 추가
- **피드백 도배 강화 (hCaptcha 등)** — 트래픽 자체가 작을 때 우선순위 낮음
- **Cloudflare 사전 적용** — DNS 변경 부담 vs 효과 미지수. 한도 임박 시점에
  결정

## 💰 전국 6000교 확장 시 비용 시나리오

**배경**: 2026-04-26 — "전국 초등학교 6000개 확장 시 운영비?" 질문 분석.
현재 76교 → 6000교는 80배 확장. 침투율(서비스 인지·사용 학부모 비율) 이
비용을 좌우하는 가장 큰 변수.

### 가정

| 항목 | 값 |
| --- | --- |
| 전체 학교 | 6000 |
| 학교당 학부모 | 600명 (학생 400 × 부모 1.5) |
| 사용자당 일 진입 | 1.2회 (점심 직전·후) |
| 진입당 함수 호출 | ~5 (페이지 + meal + photo + og 등) |

### 시나리오별 사용 규모

| 시나리오 | 침투율 | DAU | 월 함수 호출 | 월 진입 |
| --- | --- | --- | --- | --- |
| **A 보수** | 1% | 36K | 650만 | 130만 |
| **B 중간** | 5% | 180K | 3,250만 | 650만 |
| **C 낙관** | 15% | 540K | 9,720만 | 1,940만 |

**Vercel** (Pro $20/월 + 함수 1M 초과 시 1M당 $0.40):
- A: $20 + (5.5M × $0.40) ≈ **$22**

**기타** (NEIS 무료, 도메인 ~$1, cron 큐 ~$10): A·B·C 공통 ~$10

### 월 합계

| 시나리오 | 합계/월 | 연간 |
| --- | --- | --- |

### 비용 외 진짜 위험

비용보다 더 무서운 것들:

1. **학교 홈페이지 차단** — 6000개 학교 사이트를 cron 으로 매일 3회 긁으면
   시·도 교육청이 "이상 트래픽" 차단 가능. 도메인 단위 차단되면 그 도시 학교
   사진 미러 통째로 실패. → cascade failure
2. **NEIS API rate limit** — 6000교 × 5일 × cron 3회 = 9만 회/일.
   무료 키 한도 가까이 갈 가능성
3. **Supabase Bandwidth 폭증** — C 시나리오에서 1.45TB. 비용 외에도 Supabase
   가 abuse 의심으로 throttle 걸 가능성. 그 전에 Cloudflare R2 같은 외부
   Storage 로 옮기는 게 안전
4. **cron 60초 한도** — 학교 76 → 6000은 80배. 현재도 빠듯한 60초 한도
   초과 확실. 학교 그룹별 cron 분할 또는 Cloudflare Workers 큐 필요

| 침투율 | 월 비용 | 1인 운영자 부담 가능성 |
| --- | --- | --- |
| 1% | ~7만원 | 가능 |
| 5% | ~12만원 | **결정점** — 후원·기부 받기 검토? |
| 15% | ~27만원 | 단독 부담 어려움 |

### 비용 줄이는 구조적 처방 (C 도달 전 미리)

다음을 미리 깔아두면 C 시나리오 비용을 B 수준으로:

1. **Cloudflare 앞단** — 무료. Vercel·Supabase 앞에 CDN 한 겹 더 → Bandwidth
   80% 절감 가능
2. **이미지 lazy load** — viewport 밖 사진 안 받음. 진입 즉시 다운로드 ↓
3. **Service Worker 캐싱** (PWA 강화 패키지 A) — 같은 사용자 재진입 시 이미지
   재다운 X
4. **이미지 압축 강화** — JPEG q=80 → q=70, 1280px → 960px. Bandwidth 절반
5. **국토 단위 cron 분할** — `/api/cron/refresh?region=경기` 식으로 학교 그룹별
   호출. 60초 한도 분산

### A. Service Worker (오프라인 캐싱)

**무엇**: 홈 화면 추가한 사용자가 인터넷 없는 상황(지하철, 학교 무선망 끊김
등)에서도 마지막 본 화면 접근 가능하게.

**왜 보류**: PWA install 만으로도 "앱처럼" 은 충족됨. 오프라인 캐싱은
NEIS·미러 둘 다 정적이 아니라 캐싱 정책이 까다로움 (어느 시점 데이터를
보여줄지). 사용자가 실제로 오프라인 케이스 보고하기 전엔 보류.

**실행 시 점검할 것**:
- next-pwa 또는 자체 SW (Next.js 16 호환성 확인)
- 캐싱 전략:
  - 정적 자산 (icon, manifest, 폰트): cache-first
  - `/api/meal`, `/api/meal/photo`: network-first + 실패 시 stale 캐시
  - HTML 셸: stale-while-revalidate
- 캐시 만료/무효화 — 식단 바뀌면 어떻게 알릴까 (cron 시각 지나면 무효화 등)
- iOS Safari 의 SW 한계 (홈 화면 standalone 에선 SW 동작 OK, 일반 Safari 탭은
  종료 시 캐시 일부 휘발 가능)
- Service Worker 자체 업데이트 흐름 — 새 배포 후 사용자가 강제 새로고침
  안 해도 다음 진입 시 자동 갱신되는 패턴 (skipWaiting + clients.claim)

### B. 푸시 알림 ("오늘의 급식이 올라왔어요")

**무엇**: 학부모가 매일 사이트 들어오는 대신 푸시 받기.

**왜 보류**:
- 권한 요청 피로 — "이 사이트가 알림을 보내려고 합니다" 모달은 신뢰 떨어뜨림
- 학부모는 매일 같은 시간 보는 패턴이라 푸시 효용 작을 수 있음
- 푸시 인프라 (VAPID 키, FCM, 발송 cron) 운영 부담

**실행 시 점검할 것**:
- 권한 요청 시점 — 첫 진입 X. 사용자 명시 옵트인 (예: "급식 알림 받기"
  버튼) 후에만 권한 요청. 한 번 거절하면 영구 거절이라 돌이킬 수 없음
- 발송 cron — 학교마다 사진 등록 시점 다름. 14:30 cron 직후 그 학교 사용자만
  타겟팅하는 식 (subscription 에 schoolId 매핑)
- iOS 16.4+ 만 푸시 지원 → 안드/iOS 분기 + 미지원 환경 그레이스풀 안내
- VAPID 키 관리 (Vercel env var)
- 구독 저장소 — Supabase 에 `push_subscription` 테이블 (endpoint, p256dh, auth,
  schoolId, created_at)
- 사용자 토큰 만료/무효화 처리 (FCM 410 응답 시 구독 삭제)
