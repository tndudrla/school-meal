## 🍱 PWA 경험 강화 패키지 (네이티브 앱 대신 가는 길)

**배경**: 2026-04-26 — "iOS/Android 앱으로 만들면 비용?" 질문에 대한 결론.
Apple $99/년, Google $25 1회. 비영리 톤에 매년 13~14만원 부담 + Mac 필수
+ 심사 부담 → **굳이 네이티브 앱 안 만듦**.

대신 **A + B 를 추가하면 PWA 가 네이티브 앱 95% 수준의 경험** 제공:
- 홈 화면 아이콘·standalone 실행 (이미 Stage 9·11 에서 완료)
- 오프라인 동작 (A — Service Worker)
- 푸시 알림 (B — Web Push)

비용 0원, 업데이트는 git push 즉시 반영. 앱 스토어 검색 노출만 포기.

**진행 트리거**: Stage 11 의 install prompt 가 잘 동작하는 게 확인되고
사용자가 "더 앱처럼" 을 원할 때, 또는 오프라인 상황 보고가 들어올 때.

### A. Service Worker (오프라인 캐싱)

**무엇**: 홈 화면 추가한 사용자가 인터넷 없는 상황(지하철, 학교 무선망 끊김
등)에서도 마지막 본 화면 접근 가능하게.

**왜 보류**: PWA install 만으로도 "앱처럼" 은 충족됨. 오프라인 캐싱은
NEIS·미러 둘 다 정적이 아니라 캐싱 정책이 까다로움 (어느 시점 데이터를
보여줄지). 사용자가 실제로 오프라인 케이스 보고하기 전엔 보류.

**실행 시 점검할 것**:
- next-pwa 또는 자체 SW (Next.js 16 호환성 확인)
- 캐싱 전략:
  - 정적 자산 (icon, manifest, 폰트): cache-first
  - `/api/meal`, `/api/meal/photo`: network-first + 실패 시 stale 캐시
  - HTML 셸: stale-while-revalidate
- 캐시 만료/무효화 — 식단 바뀌면 어떻게 알릴까 (cron 시각 지나면 무효화 등)
- iOS Safari 의 SW 한계 (홈 화면 standalone 에선 SW 동작 OK, 일반 Safari 탭은
  종료 시 캐시 일부 휘발 가능)
- Service Worker 자체 업데이트 흐름 — 새 배포 후 사용자가 강제 새로고침
  안 해도 다음 진입 시 자동 갱신되는 패턴 (skipWaiting + clients.claim)

### B. 푸시 알림 ("오늘의 급식이 올라왔어요")

**무엇**: 학부모가 매일 사이트 들어오는 대신 푸시 받기.

**왜 보류**:
- 권한 요청 피로 — "이 사이트가 알림을 보내려고 합니다" 모달은 신뢰 떨어뜨림
- 학부모는 매일 같은 시간 보는 패턴이라 푸시 효용 작을 수 있음
- 푸시 인프라 (VAPID 키, FCM, 발송 cron) 운영 부담

**실행 시 점검할 것**:
- 권한 요청 시점 — 첫 진입 X. 사용자 명시 옵트인 (예: "급식 알림 받기"
  버튼) 후에만 권한 요청. 한 번 거절하면 영구 거절이라 돌이킬 수 없음
- 발송 cron — 학교마다 사진 등록 시점 다름. 14:30 cron 직후 그 학교 사용자만
  타겟팅하는 식 (subscription 에 schoolId 매핑)
- iOS 16.4+ 만 푸시 지원 → 안드/iOS 분기 + 미지원 환경 그레이스풀 안내
- VAPID 키 관리 (Vercel env var)
- 구독 저장소 — Supabase 에 `push_subscription` 테이블 (endpoint, p256dh, auth,
  schoolId, created_at)
- 사용자 토큰 만료/무효화 처리 (FCM 410 응답 시 구독 삭제)

### C. 이번 주 식단 한 번에 보기 (사이트에서)

**무엇**: 사이트에서도 5일 요약 카드/리스트. 지금은 일별 카드 넘기기 필요.

**왜 보류**: Stage 10 의 PNG 가정통신문이 같은 정보를 다 담음. 사이트 안에
중복 화면이 생기면 UX 혼란.

**실행 시 점검할 것**:
- 이미 있는 PNG 라우트(`/api/week`)를 사이트 안에서 그대로 보여줄지, 아니면
  HTML 으로 별도 렌더할지
- 모바일 세로 스크롤 vs 가로 스와이프

### D. 다른 시도 교육청 학교 추가

**무엇**: 서울·대구·부산 등 J10(경기) 외 지역 확장. 북극성에 가장 가까운 작업.

**왜 보류**: 도메인 패턴이 시도마다 다름. `*.goeay.kr` (경기), `*.sen.go.kr`
(서울) 등. `schoolScraper.ts` 의 `sysIdFromHost` 정규식과 미러 파이프라인
점검 필요. 한 시도씩 추가하는 게 안전.

**실행 시 점검할 것**:
- 학교 도메인 패턴 (시도별 다름)
- ATPT 코드 (서울 B10, 부산 C10, 대구 D10 등 — NEIS 문서 확인)
- mi(메뉴 식별자) 추출 정규식이 시도별 사이트 마크업과 호환되는지
- `scripts/build-school-config.mjs` 의 `ATPT` 상수가 J10 박혀 있어 인자화 필요

## 진단/모니터링

### α. Stage 12 — 카톡 사진 불발 재현 진단

**무엇**: 사용자 보고: "사진이 보일 때도 있고 안 보일 때도 있음". 비결정적
재현이라 추측 패치 없이 본격 진단 필요.

**왜 보류**: 마지막 사고 보고 이후 다른 사고 없어 우선순위 낮아짐. 다음
재현 시점에 같이 잡는 게 효율적.

**실행 시 점검할 것**:
- 카카오 OG 디버거 (`developers.kakao.com/tool/debugger/sharing`) 로 실시간
  메타·이미지 응답 확인
- `/api/og` 의 mirroredPhotoUrl 조회 → 미러 hit 인데도 카톡이 못 받는 케이스
  vs 미러 miss 라 텍스트 카드로 떨어진 케이스 구분
- Vercel Analytics 의 OG 라우트 응답시간/상태코드
- Cache-Control 1시간 + stale-while-revalidate — 카톡 봇이 stale 응답을
  먼저 캐싱했을 가능성

### β. 사진 미러 실패 알림 (운영 모니터링)

**무엇**: cron 응답에서 학교별 실패 카운트가 일정 임계 넘으면 Slack 알림.
75개 학교 → 1~2개가 매번 실패해도 묻혀있음.

**왜 보류**: Slack 알림 hook 인프라 (Stage 9 직후) 는 있으나, cron 응답을
파싱해 임계 비교하는 별도 로직이 없음. 우선순위 중간.

**실행 시 점검할 것**:
- cron 응답 JSON 의 `failed/missing` 카운트
- 임계값 (예: 학교 5% 이상 실패 시 알림)
- Slack webhook 으로 학교명·실패 사유 한 줄 전송
- 새 cron 슬롯(14:30, 17:00)에서 미러 결과 안정화 후 추가하면 더 정확
